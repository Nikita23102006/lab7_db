## Учебная база

Задания на sqlite3 и на SQLAlchemy используют одни и те же данные
из `university_data.py` — четыре таблицы:

```
groups ──< students ──< grades >── courses
```

- `groups` — учебные группы;
- `students` — студенты, внешний ключ на группу, email уникален, стипендия ≥ 0;
- `courses` — дисциплины;
- `grades` — оценки, составной первичный ключ (студент, дисциплина), оценка от 2 до 5.

Данные подобраны так, чтобы были видны крайние случаи: группа без студентов,
студент без оценок, дисциплина, по которой никто не получил оценку.
Схема для sqlite3 создаётся в `db_setup.py`.

## Описание решений

### Средней сложности №8 — выполнить JOIN

Шесть запросов, показывающих разные виды соединений:

| Запрос | Что показывает |
|---|---|
| студенты и группы | `INNER JOIN` — только совпадающие строки |
| группы и число студентов | `LEFT JOIN` — пустая группа видна с нулём |
| ведомость | `JOIN` четырёх таблиц |
| студенты без оценок | `LEFT JOIN … WHERE … IS NULL` |
| статистика по дисциплинам | `LEFT JOIN` + `COUNT` и `AVG` |
| средний балл групп | `JOIN` + `GROUP BY` + `HAVING` |

Для наглядности выводится число строк при `INNER` и `LEFT JOIN`
на одних и тех же таблицах: 8 и 9. Отдельно объяснено, почему для пустой
группы нужно `COUNT(s.id)`, а не `COUNT(*)`.

### Средней сложности №10 — SQLAlchemy для одной таблицы

Модель `Product` (склад товаров) в стиле SQLAlchemy 2.0:
`DeclarativeBase`, `Mapped[...]`, `mapped_column`, запросы через `select()`.
Ограничения задаются в модели: уникальное имя, индекс по категории,
`CheckConstraint` на цену и количество.

Показаны: выборка с сортировкой и печать сгенерированного SQL, фильтры
`where`, `LIKE`, получение по ключу `session.get`, изменение через атрибут
объекта, вставка, массовые `update()` и `delete()` без загрузки объектов,
агрегаты `count` и `sum` с группировкой.

### Средней сложности №4 — обновить запись

- изменение одного поля и нескольких полей сразу;
- перевод в другую группу — подзапрос в `SET`, защита от несуществующей группы;
- массовое обновление по условию: +10 % стипендии студентам со средним
  баллом не ниже 4,5 (подзапрос с `GROUP BY` и `HAVING`);
- проверка `rowcount`: обновление несуществующей записи не вызывает ошибку,
  а возвращает 0;
- нарушение ограничения `UNIQUE` → `IntegrityError` → `rollback()`.

Значения передаются только параметрами `?`. Имена колонок параметром передать
нельзя, поэтому функция `update_student` принимает только колонки из
разрешённого списка — попытка подставить что-то другое даёт `ValueError`.

### Повышенной сложности №1 — SQLAlchemy с несколькими таблицами

Четыре модели и два вида связей:

- **один-ко-многим**: `Group.students` ↔ `Student.group`;
- **многие-ко-многим** между `Student` и `Course` через модель `Enrollment`,
  в которой хранится оценка (association object).

Показаны переходы по связям в обе стороны, `join()` по связи с агрегатом,
добавление объекта через связь (внешний ключ ставится автоматически),
каскадное удаление оценок вместе со студентом (`cascade="all, delete-orphan"`).

Отдельно продемонстрирована **проблема N+1**: при ленивой загрузке обращение
к оценкам восьми студентов даёт 9 запросов к базе, с `selectinload` — 2.
Запросы считаются через событие `before_cursor_execute`.

### Повышенной сложности №8 — кэширование запросов

Класс `QueryCache` и обёртка `CachedDatabase`:

- ключ кэша — нормализованный текст запроса и параметры;
- **сброс по таблице**: запрос на запись сбрасывает все закэшированные
  запросы, читавшие из этой таблицы; запросы к другим таблицам остаются;
- **срок жизни** записи (TTL);
- **ограничение размера** с вытеснением давно не использованных (LRU,
  на `OrderedDict`);
- статистика попаданий и промахов.

Тяжёлый запрос — посещаемость по 300 000 строк — из кэша выполняется
в тысячи раз быстрее. В конце показано, почему `functools.lru_cache`
для запросов к базе опасен: после `UPDATE` он продолжает возвращать
устаревший результат.

## Связь заданий

- `task04_update.py`, `task08_join.py`, `adv08_query_cache.py` используют общую
  схему из `db_setup.py`;

- `main.py` сравнивает ведомость, полученную `JOIN` на чистом SQL (задание №8),
  с ведомостью через связи ORM (повышенное №1) — они совпадают построчно.
